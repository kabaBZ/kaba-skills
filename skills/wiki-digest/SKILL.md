# 消化

用于将 `raw/` 中的原始资料消化为 `wiki/` 中的原子化知识笔记。若用户指定一个或多个文件，则只处理这些文件；若未指定，则自动处理 `raw/` 中最近的一个文件。消化过程遵循 Atomic Notes 原则，将内容拆解为多个独立、单一主题、可链接、可复用的知识条目，而不是合成一篇笼统总结。避免重复；建立连接时可以读取 index 文件，非必要不要全量读取所有文件。进行改动后要更新 index 文件和 log 文件。

你负责把 `raw/` 中的原始资料整理为 `wiki/` 中的知识条目。执行时，先判断用户是否明确指定了文件：如果指定了一个或多个文件，则只处理这些文件；如果没有指定，则自动选择 `raw/` 目录下最近修改的一个文件进行处理。处理原则遵循 Atomic Notes：每条笔记只表达一个明确主题或一个独立知识单元，不要把多个概念、多个论点、多个案例混写在同一条笔记里。每条笔记必须能够脱离原始上下文单独理解，标题应当清晰、具体、可检索，最好本身就是一句完整判断或一个明确名词短语。不要直接照搬 raw 内容，也不要只做摘要；你需要把内容拆解、改写、提炼成可以长期复用的知识单元。拆解时，优先提取概念、事实、方法、证据、观点这几类内容；如果一段内容中包含多个意思，就拆成多条笔记。笔记之间应尽量建立关联，补充相关条目、回链建议和标签，避免形成知识孤岛。对于不值得沉淀为独立条目的信息，可以舍弃，不要为了完整而制造低价值笔记。若一次传入多个 raw 文件，应将它们视为同一轮 digest 的输入，统一规划页面拆解、去重、链接以及 `wiki/index.md` 与 `wiki/log.md` 的更新，而不是把它们当成多个彼此独立的小任务顺序处理。

## 约定与风格

- 操作原则：不确定时，先提议再执行，不做大规模自动改动。
- 页面命名：中文 + 下划线，稳定可读（如 `概念_费曼学习法`）。
- 内部链接：使用 Obsidian `[[wikilink]]` 语法。
- 不确定时：先提议“创建/修改哪些页面”，由用户确认后再执行。
- 当需要查找笔记间的关系时，优先使用 `obsidian-cli` 类能力或等价的链接/元数据查询方式，而不是全量盲读。

## schema

维护 `wiki/` 目录，将其打造为可复利的知识层。

- 原始资料（`raw/`）是唯一事实来源，只读不改。
- 只在 `wiki/` 里创建、修改 Markdown 页面。
- 不要动其它目录。

目录建议：
- `wiki/sources/`：单个来源的摘要页
- `wiki/entities/`：人物、书籍、项目等实体页
- `wiki/concepts/`：方法、理论、模型等概念页
- `wiki/comparisons/`：比较分析页
- `wiki/overview/`：总览、综合页
- `wiki/index.md`：内容索引
- `wiki/log.md`：操作日志

### 所有 wiki 页面顶部建议使用 frontmatter：

```yaml
---
type: "source|entity|concept|comparison|overview"
tags: ["tag1", "tag2"]
summary: "一句话说明这页的核心内容"
sources: ["raw/xxx.pdf", "raw/yyy.md"]
updated: "2026-04-08"
---
```
### Source Summary（来源摘要页）

路径：`wiki/sources/xxx.md`

- 来源信息（标题、作者、时间、链接）
- 核心要点（3–7 条 bullet）
- 关键引文（可选）
- 关联实体/概念链接（`[[entities/xxx]]` / `[[concepts/yyy]]`）

### Entity Page（实体页）

路径：`wiki/entities/人物_马斯克.md` 等

- 基本信息
- 行为 / 特征 / 状态
- 相关事件 / 计划 / 实验链接
- 来自哪些来源（列出 `sources`）

### Concept Page（概念页）

路径：`wiki/concepts/概念_费曼学习法.md` 等

- 定义
- 使用场景 / 步骤
- 在本知识库中的应用示例
- 关联实体 / 其它概念

### Comparison Page（比较页）

路径：`wiki/comparisons/xxx_vs_yyy.md`

- 比较对象简介
- 相同点
- 不同点（目标、成本、适用场景…）
- 结论 / 选择建议

### Overview / Synthesis（总览 / 综合）

路径：`wiki/overview/主题_儿童自驱学习_综述.md` 等

- 一句话结论（Summary）
- 当前理解 / 总体框架
- 支撑它的主要来源和页面链接
- 未决问题 / 待验证假设

## 工作流

当用户调用 `/wiki-digest` 时：

1. 判断是否指定了一个或多个 `raw/` 文件；未指定则选择最近修改的一个。
2. 读取这些原始资料，拆分出适合沉淀的原子知识单元。
3. 在同一轮 digest 中统一去重、合并交叉主题并规划页面链接。
4. 在 `wiki/` 中创建或更新合适的页面类型。
5. 只在必要范围内读取现有 `wiki/index.md`、相关页面与 `wiki/log.md`，避免全量扫描。
6. 更新 `wiki/index.md`，补上新页面条目与一句话 summary。
7. 更新 `wiki/log.md`，追加本次 digest 记录。
8. 如果将产生较大范围改动，先给出拟改动页面清单，等用户确认后再执行。

## 工作流模式

当这个技能被上层工作流显式传入一个或多个 `raw/...` 路径时：

- 只处理这些指定 raw 文件，不要再自动猜最近文件。
- 默认直接执行对应的入库写入，而不是退回成纯建议模式。
- 若一次传入多个 raw 文件，应把它们作为同一批输入统一 digest，而不是拆成多次顺序调用。
- 输出中应明确返回：
  - 新建或更新了哪些 `wiki/...` 页面
  - 是否更新了 `wiki/index.md`
  - 是否更新了 `wiki/log.md`
- 若拟改动范围明显超出这批 raw 文件自然引出的必要范围，先报告再执行。

## 输出要求

- 默认优先执行实际文件改动；如果上下文不足，先给出拟新增/修改页面列表。
- 不直接复制 raw 原文。
- 产物应可长期复用、可独立理解、可被其他页面链接。
- 在工作流模式下，输出应足够结构化，便于上层汇总多个 digest 结果。
